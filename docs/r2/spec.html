01 · The flow

Paste, and walk away

The same R1 pipeline turned on a whole playlist — one track at a time (ADR-001, sequential), one card, one stream.

1

Expand

The playlist URL that R1 rejected with a 422 is now accepted. yt-dlp expands it into N tracks; each becomes its own jobs row and runs the existing download → transcode → identify → tag → land pipeline.

2

Mirror to Jellyfin

A Jellyfin playlist named after the YouTube title is created and filled as tracks land. Each file still lands canonically under Artist/Album — one copy on disk; the playlist holds pointers.

3

Park the messy ones

Low-confidence tracks go to the same R1.1 review inbox — no second place to look. The batch reports "waiting on you," not "done," while any track is still parked.

4

Backfill & re-run

Resolve a parked track days later and it appends to its playlist automatically. Re-paste a grown playlist and it updates the same Jellyfin playlist, silently skipping videos already owned.

02 · Problem

A 50-song month is 50 pastes — and the month is lost anyway

The manual grind

The owner curates music by month — a YouTube playlist per month, a personal "music journal." Today that music enters the clean library one song at a time. A 50-song month is 50 manual pastes.

Worse: nothing in Jellyfin preserves the month. The grouping that is the whole point of the journal vanishes the moment songs land under Artist/Album.

T-037, multiplied latent defect

The shared tagging path writes some artist credits mangled — a JAY-Z → JAŸ-Z encoding fault — splitting one artist across multiple library folders.

On single-song acquire it bites rarely. A 50-song batch multiplies every occurrence, so R2 fixes it in the write path.

03 · Data model

One playlist, many track-jobs, one stream

The batch reuses the per-song job unchanged — so the entire R1/R1.1 pipeline and the review lifecycle are reused. A single nullable column is the switch that keeps R1 byte-for-byte untouched.

playlists new entity

  • idprimary key
  • youtube_playlist_idthe keyunique
  • titlederived from YouTube, not entered
  • jellyfin_playlist_idthe created playlistnullable
  • created_attimestamp

jobs 3 fields added

  • playlist_idnull = single paste (R1 path)nullable FK
  • positionindex in the expanded playlist
  • youtube_video_idsource video — durably recorded for dedup
Null playlist_id = R1 unchanged. Non-null = a batch member. This is the whole switch.
One SSE stream per batch, never per track. Browsers cap ~6 EventSources per origin, so 50 cards would leave 44 streams dead. The batch opens one playlist-scoped stream; the server fans each track's events onto it, every event stamped with the track's position/job id.

05 · Key decisions

The three seams that carry the risk

De-duplication — exact video only, never fuzzy

On expansion, each entry's video ID is matched against the library's record of landed videos:

Hit → skip download/identify/tag entirely; add the existing canonical file to the playlist; emit track.skipped. Silent — not the ADR-009 duplicate-park path.
Miss → normal pipeline. A genuinely different upload of an owned song is treated as new — an accepted duplicate-file risk, so no wanted song is ever silently swapped out.

Jellyfin output new seam

jellyfin.py gains create-playlist, resolve landed-file → item ID, and append-item — extending the single existing seam, no second integration point.

Timing seam: an item ID exists only after Jellyfin's async scan. The append must wait for/resolve the item post-scan — specified in the ADR. App-side membership is the source of truth, read three ways: idempotent re-paste, counters, backfill.

Backfill — review → playlist

The locked chain, walked when a parked track resolves and lands:

review→ job→ playlist→ jellyfin_id

Append to end — position not preserved. Original position is recorded so the list isn't actively scrambled, but no effort is spent re-inserting (owner decision).

T-037 — artist-credit normalisation in scope · new ADR

Defect 1 — the split. Diagnosed: MusicBrainz's canonical credit uses a Unicode hyphen (U+2010) and the Y is mangled to Ÿ (U+0178) in the write path. R2 adds a canonical normalisation step in the path-format path so no fresh download re-introduces a mangled folder.

Defect 2 — missing genre. Mostly closed: the plugin/key theories were already refuted; a bare genre is real Last.fm coverage, not a bug. The one genuine fix: Outcome.tags snapshots before lastgenre writes, so the card claims "no genre" on a file that has one. Fix the snapshot so track.done carries the genre actually written.

08 · Scope

What R2 is — and pointedly isn't

In scope

  • +Playlist acquire — expand, process sequentially, mirror to a Jellyfin playlist.
  • +Exact-video de-dup + idempotent re-paste.
  • +Backfill from the review inbox on resolve.
  • +One aggregate batch card (design gate first).
  • +T-037 artist-credit normalisation + genre-report fix.

Out of scope

  • →Migrate / clean the existing library — split to R2.5. R2 is acquisition only.
  • →Loose multi-URL paste — lighter feature, deferred.
  • →"Recently Added" rolling playlist — needs a recomputed mechanism.
  • →User-named playlists — rejected; the name is derived to keep friction zero.
  • →Preserving exact backfill position — append-only.
  • →Parked backlog — T-034/035/042/023/030/031/032/039/041 each ride their own release.
09 · Prerequisites

Two ADRs and a gate — before component code

The mockups encode these decisions; writing them after the gate means re-mocking. Retrofitting the association into live job data later is unrecoverable.

ADR · new

Batch / backfill data model

playlists + job.playlist_id + the review→playlist append + the Jellyfin item-ID timing seam. Settled before the design gate.

ADR · new

T-037 credit normalisation

Binds every path the app writes — the Ÿ→Y fold and the hyphen decision recorded there.

ADR-016 · applies

Design gate

Changes a user-visible flow/state → flat HTML scenario screens, including the ugly states, published for owner sign-off first.

Hard constraints hold (ADR-001–005): sequential processing (a batch is a queue, one live track), MP3 320 output, one-failure-continues-the-batch, single-user / no-auth, beets-not-hand-rolled.
10 · Acceptance

R2 is "done" when…

To expand into docs/r2/tickets.md. The observable artifact (DoD step 3): a /verify run pastes a small real playlist end-to-end and confirms the real side effects.

  • Pasting a playlist URL expands it and processes every track sequentially over one SSE stream.
  • A Jellyfin playlist named after the YouTube title is created and populated as tracks land.
  • Each file lands canonically under Artist/Album; one copy on disk, playlist holds pointers.
  • A parked track resolved later appends to its playlist automatically.
  • Re-pasting the same grown playlist updates the same playlist, skips already-have videos silently, adds only new entries.
  • An exact-video duplicate is skipped and added to the playlist; no fuzzy matching occurs.
  • A failed track doesn't stop the batch; the batch reads "waiting on you" while parked > 0.
  • The batch view is one aggregate card (design-gate screens signed off first).
  • A fresh download of a T-037-class artist lands under the single canonical folder.
  • track.done reports the genre actually written to disk.
  • Single-song acquire (R1) is unchanged.
  • Suites green on main; a /verify run shows the real playlist created and backfilled.
