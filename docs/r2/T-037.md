# T-037 — Two tag-quality defects observed on a real auto-tag landing

> **Backlog (triage needed).** Both surfaced 2026-07-28 while hunting a parked track for T-106's
> gate — incidental findings on a track that auto-tagged instead. Neither blocks R1.1. See
> `docs/backlog/README.md` for how this directory works.

- **Status:** todo — **filed unreviewed 2026-07-28, owner has not triaged.** Two independent defects on
  the same landing; split into separate tickets if triage disagrees about priority.
- **The subject.** Jay-Z — *Wishing on a Star (feat. Gwen Dickey)*
  (`https://youtu.be/ZyDslhDin4s`) auto-tagged and landed at
  `/mnt/c/Users/aj_am/Music/CleanMuzik/Jay-Z/Wishing on a Star (feat. Gwen Dickey).mp3` — 323 kbps,
  cover art embedded (mjpeg stream), title/artist/date written. The pipeline worked. These are the two
  things wrong with what it produced.

## Defect 1 — the same artist lands under two different folders

The library now holds **both** `JAŸ‐Z/` (from *Coming of Age*, landed 2026-07-19) and `Jay-Z/` (this
track). Same human, two directories, so **Jellyfin will list two artists** and neither page shows the
full discography.

- **Cause (probable, not verified).** beets derives the path from the MusicBrainz *artist credit* on the
  matched release, and MB genuinely records this artist's credit differently per release — the stylised
  `JAŸ-Z` on some, plain `Jay-Z` on others. So both are "correct" per the match; the split is a
  consequence of trusting per-release credit for the *directory* name.
- **Why it matters more than it looks.** It is invisible on the first track by an artist and appears on
  the second — so it will keep accruing quietly as the library grows, and every occurrence is a manual
  merge later. The owner's library is the point of the product.
- **The shape of a fix (undecided).** beets' `%aunique`/path-format options and the `albumartist` vs
  `artist` distinction are the obvious levers; an artist-credit → canonical-name normalisation
  (ASCII-folding stylised glyphs, per ADR-019's note that folding affects ranking not identity) is the
  other. **Do not** pick one here — this needs a decision recorded as an ADR, because it binds every
  future path the app writes.

## Defect 2 — no genre tag was written

`genre` is absent on the landed file. `album` is absent too. The `lastgenre` plugin is loaded (the boot
smoke check confirms all six plugins), and **T-106's own July artifact recorded `genre Hip Hop`** on the
Nines track — so this is a change in behaviour, not a feature that never worked.

- **Candidate causes, none verified.** Last.fm has no tags for this recording; the owner's
  `LASTFM_APIKEY` is being rejected (it is present in `.env`); `lastgenre`'s source/fallback settings
  don't cover a singleton import; or the absent `album` and absent `genre` share a cause upstream in
  what the match returned.
- **Cheap first probe.** Re-run a track that previously *did* get a genre and compare — if it also comes
  back bare, the plugin or the key regressed; if it doesn't, this is per-recording Last.fm coverage and
  arguably not a defect at all.

The landed MP3 carries the full YouTube `SYNOPSIS`/`DESCRIPTION` (label marketing copy and social

## Candidate approach for defect 1 (owner, 2026-08-05, from a live duplicate panel)

Seeing `JAŸ-Z` render verbatim on both sides of a duplicate review, the owner proposed an
**LLM cleanup sweep** — "for every Jay-Z track, make it follow this standard." Sound for the
*one-time library tidy*, but it only answers half the ticket:

- **One-time sweep** (fix what's already on disk): an LLM pass, or even a plain fold/replace rule,
  is fine here — bounded and reviewable.
- **Every future write** (a fresh paste never re-introduces `JAŸ-Z`): cannot be an ad-hoc run; the
  normalisation must live in the pipeline. This is the half that *needs the ADR*, because it binds
  every path the app writes. Do the sweep without it and the folders re-split on the next download.

So the LLM idea is a good answer to the first half, not a substitute for the decision the ticket asks for.

## Defect 1 recurred on a real replace + the cause is now diagnosed (2026-08-05)

Defect 1 bit again in live use, and hard enough to sharpen the cause from "probable" to diagnosed.

- **How it recurred.** The owner downloaded *My 1st Song* (the explicit cut), which parked as a
  **duplicate** of the clean version already at `Jay-Z/My 1st Song.mp3`, and resolved it from the inbox
  with **Replace**. The mechanism worked — old file gone, new one landed — but the new file organised to
  **`JAŸ-Z/My 1st Song.mp3`**, splitting it from the owner's other Jay-Z tracks, and **orphaned the old
  `Jay-Z/My 1st Song.lrc`** sidecar (deleted the MP3, left its lyrics behind in the old folder). So the
  split isn't only an acquire-time cosmetic — on a *replace* it silently strands a sidecar too.
- **Full extent at the time (library scan).** "Jay-Z" was split across **three** folders —
  `Jay-Z/` (canonical), `JAŸ-Z/` (*My 1st Song*), `JAŸ‐Z/` (*Coming of Age*, since 2026-07-19).
- **The cause, now diagnosed (was "probable, not verified").** It is **not** merely "MB records the
  credit differently per release." It's an **encoding fault** on top of MB's stylised spelling:
  - MusicBrainz's canonical credit for this artist is **`JAY‑Z`** with a Unicode hyphen **U+2010** (`‐`),
    not the ASCII hyphen-minus U+002D (`-`).
  - The **`Y` is being mangled to `Ÿ` (U+0178, Latin capital Y with diaeresis)** somewhere in the
    write path — a classic mojibake of the byte(s) for `Y`.
  - The two corrupt variants differ only in the **hyphen**: `JAŸ-Z` (U+002D) vs `JAŸ‐Z` (U+2010) — i.e.
    the same `Y→Ÿ` corruption, once with MB's original U+2010 hyphen preserved and once normalised to
    ASCII. The owner's canonical `Jay-Z/` uses plain `Y` + U+002D.
  - **Both corrupt items carried `mb_trackid`s** (`5e805bda…`, `3566c623…`) — they *matched* MusicBrainz,
    so the bad string rides the **matched-metadata path**, not a no-match tag fallback. That narrows the
    fix target: the corruption is in how the matched artist-credit is decoded/written, and a canonical
    normalisation step (fold `Ÿ→Y`, and either normalise the hyphen or accept MB's) belongs in the
    pipeline per the ADR this ticket already calls for.
- **One-time tidy: done for Jay-Z (precedent for the sweep half).** All three consolidated into a single
  `Jay-Z/` with tag **and** beets-DB updated (via `Item.try_write()` + `Item.move()`, not a blind `mv`,
  so future dup-detection paths stay consistent), sidecars reattached/deduped, empty mojibake folders
  removed, beets DB backed up first, Jellyfin rescan triggered. This is a working recipe for the
  "one-time sweep" half — but the **pipeline/ADR half is unchanged**: the next affected download
  re-introduces `JAŸ…`. Not Jay-Z-specific — any artist whose credit trips the `Y→Ÿ` decode will split.
