# T-213 — Re-extract-on-403 retry for the download stage

**Status:** untriaged
**Found:** 2026-08-12 (owner hit it live during a real acquire; self-resolved on re-paste)
**Recurred:** 2026-08-13 — **twice in one session.** Second hit was `youtu.be/IaQjlagBnG0`
(Pa Salieu – Frontline, a Mixtape Madness channel-name upload — the marquee ISRC-correction
case). A clean repro that evening confirmed it: metadata `extract_info(download=False)`
succeeded (public, 5 audio formats) and a fresh full download of the same URL to a temp dir
**succeeded**, so the job's failure was the transient 403 again, not the video. Two
self-healing 403s at single-user volume in one evening nudges this above "rare fluke" — and
here it blocked the exact track R1.5 was built to correct.

## Problem

A real download failed at the media-fetch step:

```
Download failed: ERROR: unable to download video data: HTTP Error 403: Forbidden
```

on `watch?v=nC1nQXVlVkU&list=RDnC1nQXVlVkU&start_radio=1`. The URL shape was **not** the
cause — `is_playlist_url` correctly treats a `list=RD…` alongside a named `?v=` as a single
song, and `noplaylist=True` held the one-song line; it reached Download and failed there.
Re-submitting the plain share link succeeded immediately.

This is YouTube's transient 403: the extraction handed back a stale/throttled stream URL,
and yt-dlp's internal HTTP retries reuse the **same** poisoned player response, so they
don't recover it. A fresh `extract_info` (which is what the owner's re-paste forced) gets a
new player response with new stream URLs and works. Today a single 403 kills the track and
the owner must notice and re-paste by hand.

## Not staleness — yt-dlp is already current

Checked at the time: installed `yt-dlp==2026.7.4` **is** the latest stable on PyPI (only
`.dev` nightlies are newer, which we don't run). So a version bump would not have helped;
`server/scripts/check-ytdlp.py` was added to make that comparison a one-command check
instead of guessing from version age.

## Possible fix (deferred)

In `download.py`, wrap `ydl.extract_info(url, download=True)` in a **bounded retry that
starts extraction over** (a fresh `YoutubeDL`/`extract_info`, not just the HTTP fetch) when
the error is a 403 — e.g. up to 2 retries with a short backoff. Scope it to 403 (and maybe
`fragment`/`nsig` failures); leave genuine not-found / private / geo errors terminal so a
real dead link still fails fast per the one-failure-continues-the-batch rule (ADR-002).

## Why deferred

- It self-resolved with a re-paste; single-user, low frequency.
- Adds a retry loop to the load-bearing download path — wants its own `/verify` against a
  real 403 (hard to reproduce on demand) rather than a rushed change at session end.
