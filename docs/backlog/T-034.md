- **The finding.** Track pasted: `All Get Right ft. J Stone - Nipsey Hussle (Crenshaw Mixtape)`.
  AcoustID returned **no fingerprint match** (this mixtape rip isn't in AcoustID's DB — expected,
  see "Why AcoustID first" below). beets then fell back to a **MusicBrainz text search**, which
  returned 5 junk candidates at **0.39–0.45** (auto-accept bar is 0.90, so it correctly parked with
  `rec=none`). Root cause: the YouTube title is **reversed** — `Title - Artist`, not the conventional
  `Artist - Title` — so beets parsed:
  ```
  All Get Right ft. J Stone   -   Nipsey Hussle (Crenshaw Mixtape)
  └──── parsed as ARTIST ─────┘   └──────── parsed as TITLE ───────┘   (both inverted)
  ```
  and searched MusicBrainz for the wrong artist and wrong title. **The song is in MusicBrainz,
  cleanly** — a direct `title:"All Get Right" artist:"Nipsey Hussle"` query returns **3 exact hits
  at score 100** (*All Get Right — Nipsey Hussle, J. Stone*). MusicBrainz had the answer; beets asked
  the wrong question. Garbage in, garbage out.

- **yt-dlp probe (2026-07-24) — there is a stronger signal than the title.** Ran yt-dlp metadata-only
  on the video (`G3CwMb1IvDU`): `track` / `artist` / `album` all `None` (no YouTube-Music structured
  fields — so AcoustID + the *title* really are on their own), **but** `channel` = `uploader` =
  `"Nipsey Hussle"`, `categories` = `["Music"]`, and `tags` carries clean tokens `"all get right"` +
  `"nipsey hussle"`. So this is the **official artist channel**, not a random re-upload, and the artist
  is sitting in `channel`/`uploader` — a signal `download.py` currently **discards** (it embeds only
  what `FFmpegMetadata` writes: title + structured tags; channel/uploader/tags are dropped). Handing
  beets `artist="Nipsey Hussle"` would sidestep the reversed-title parse entirely. **This reframes the
  ticket: the primary lever is signal-selection (Layer 0 below), not the regex work.** It also revises
  the earlier "no authoritative source exists, tuning-only" read — for artist/Topic-channel uploads an
  authoritative artist *does* exist; we just weren't reading it.

- **Why it's real but not urgent.** Single-user tool, and the gate did the safe thing — nothing was
  mistagged; the track sits in review awaiting a Reject. The cost is a *rescue miss*: a track that a
  cleaned-up query would have matched instead falls to manual review. Worth fixing because it's a
  whole **class** of YouTube rips (reversed order, `ft.`/`feat.` credits, `(… Mixtape)` / `(Official
  Video)` / `(Lyrics)` cruft), and it compounds hard in **R2 migrate**, where the input is a library
  full of exactly these filenames.

- **Scope of the current normalization (verified against `app/normalize.py`, 2026-07-24).**
  `normalize_title(raw, artist=None)` runs three pure moves, in order:
  1. `_strip_promo_brackets` — drops a `()`/`[]`/`{}` group **only when every word is promotional**
     (`_PROMO_WORDS`: official/video/audio/lyrics/… + resolution tags). "When in doubt, keep it."
  2. `_strip_promo_pipe_segments` — drops `|`-delimited promo tails (`Song | Official Video` → `Song`).
  3. `_strip_artist_prefix` — strips a leading `<artist> - ` **only when `artist` is known** (from the
     download's embedded tag), matching the exact artist string.
  The Nipsey title survived all three: `(Crenshaw Mixtape)` isn't pure-promo (kept), there's no `|`,
  and the artist was unknown (YouTube rip, no embedded tag) **and** on the wrong side of the dash
  anyway. So the raw string reached beets, which split it on the dash into `artist="All Get Right ft.
  J Stone"`, `title="Nipsey Hussle (Crenshaw Mixtape)"` — inverted. **This is the ground truth to
  build on; don't re-derive it.**

- **Reality check — what regex can and can't do here (read before scoping).** This applies to the
  *title-parsing* layers (1–2); Layer 0 above is the better path where a channel artist exists and
  avoids the string-parsing trap entirely. Cruft-stripping is
  deterministic pattern surgery and genuinely *is* a few regexes (Layer 1 below). The **inversion is
  not a regex problem at all** — no pattern can know `Adele - Hello` from `Hello - Adele`; both sides
  are just words around a dash. That half needs a comparative signal against MusicBrainz (Layer 2), a
  network round-trip, not a pattern. And **nothing here reaches 100%**: titles are adversarial (no
  dash, multiple collaborators, emoji, non-Latin script, both orderings scoring low). Per the module's
  own contract, this improves *ranking*, not beets' confidence `rec` — it lifts the **rescue rate**,
  it does not eliminate review. The review queue + Reject remain the backstop for the unmatchable, and
  an AcoustID fingerprint hit stays the only path to *certainty* (ADR-006). Scope this as a measured
  match-rate improvement, **not** a "no more reviews" fix.

- **Approach — one design-level lever + three tuning layers. Do Layer 0 first; it makes the reversed-
  title problem moot for the whole artist/Topic-channel class. Stop when lift flattens.**

  **Layer 0 — confirm the artist by matching `channel` against the title's dash-segments (design-level,
  highest leverage where it applies).** yt-dlp already fetches `channel`/`uploader` (in the `info`
  dict, just not embedded). The mechanism is **not** "trust the channel as the artist" — that
  *regresses* the aggregator case (see failure mode). It's: split the title on its dash(es), normalize
  each segment (lowercase, drop `ft.`/cruft), and check whether `channel` matches one of them.
  - **Channel matches a segment** (Nipsey: `channel "Nipsey Hussle"` ≈ the *right* segment of
    `All Get Right ft. J Stone - Nipsey Hussle …`) → the channel both **confirms the artist and reveals
    which side of the dash it's on**, so artist=channel, title=the other segment. Solves Layer 2's
    inversion for free, no network round-trip.
  - **Channel matches no segment** (Trap Nation: `channel "Trap Nation"` vs `Illenium - Good Things
    Fall Apart`) → the channel is an aggregator/uploader, not the artist. **Ignore it** and fall back
    to normal parsing (which already gets `Illenium` right today).
  Gate on `categories` containing `"Music"`. **Failure mode this design exists to prevent:** a naive
  "channel = artist" override would feed `artist="Trap Nation"` into an already-correct query and turn
  a working match into a parked miss — a *regression*, not a no-op. The segment-match is the guard: the
  channel is trusted only when the title itself corroborates it.
  - **Residual edges (name them in the build):** (a) *bare title, no dash* (`All Get Right`, channel
    `Nipsey Hussle`) — nothing to match, but nothing to conflict either; seeding the channel is
    low-risk, allow it. (b) *`- Topic` channels* usually already carry a structured `artist`, handled
    by the existing embedded-tag path; the channel heuristic is their backstop. (c) *fuzzy match*
    (`IlleniumOfficial` vs `Illenium`) needs normalization/containment, not exact equality — this is
    where the care goes.
  This is the fix for the *design* gap the probe exposed; Layers 1–2 cover what Layer 0 can't (no
  usable channel, or the title is the only signal). It stays cheap (pure, no network) — the earlier
  "hint the score arbitrates" framing was wrong; the segment-match is what makes it safe, not a
  downstream scored comparison.

  **Layer 1 — cruft stripping (pure, in `normalize.py`; low-risk; helps every path).** Extend the
  existing pure function — this is the "few regexes" part, and it's realistic:
  - Strip **inline** `ft.`/`feat.`/`featuring …` credits (today features are only handled *inside*
    brackets; a bare `ft. J Stone` is untouched). Features aren't part of the canonical title.
  - Strip **context parentheticals** by keyword — add `mixtape`, `album`, `ep`, `deluxe`, `explicit`,
    `clean`, `bootleg` to a context set so `(Crenshaw Mixtape)` drops like `(Official Video)` does.
    Keyword-gated, *not* "strip all parens" (that would eat real qualifiers like `(Live)`/`(Remix)` —
    the exact mistake the current `_PROMO_WORDS` design avoids).
  - This reduces the example to `All Get Right - Nipsey Hussle`. Cleaner — but **still reversed**.

  **Layer 2 — inversion, via scored retry (NOT regex; lives in the import seam, not `normalize.py`).**
  A blind swap is wrong — most titles genuinely *are* `Artist - Title`. Instead, on the fallback path
  run the search **both ways** (`A - B` and `B - A`) and keep the ordering whose candidates score
  higher. Self-correcting with **no artist dictionary** to maintain: correct order wins when it was
  right, swap wins when reversed (surfacing *All Get Right — Nipsey Hussle* at score 100). Cost: one
  extra MusicBrainz query, only when the fingerprint already missed. Needs a floor guard so a
  genuinely-unmatchable track (both orderings weak) still parks rather than accepting the "less bad"
  side.

  **Layer 3 — guardrails (non-negotiable).** Runs **only when AcoustID returned no fingerprint match**
  (hits bypass all of this). **Never lowers the 0.90 auto-accept bar** — a cleaner query may push a
  real match *above* the bar; it may not relax the bar to admit a weak one. That line is what keeps
  ADR-006 intact.

- **Architectural boundary (don't cross it).** Layer 1 stays inside `normalize.py` — pure, no I/O,
  unit-testable by contract (the module's stated guarantee). Layer 2 does **not** belong there:
  issuing a second query and comparing scores is network I/O against MusicBrainz and belongs in the
  **import seam** (`app/import_seam.py`, the matching path). Folding a network retry into a documented
  pure function is exactly the kind of quiet contract break the review gate exists to catch.

- **How to measure (so "better" isn't a vibe).** Before/after, count how many current parked reviews
  each layer would rescue. For Layer 0: how many parked jobs came from a `categories: Music` upload
  whose `channel`/`uploader` names an artist MusicBrainz knows. For Layer 1: re-run normalization +
  text search over the stored queries. Build each successive layer only if the prior leaves real
  matches stranded — later layers earn their cost by measured lift, not by theory.

- **Done when:** a decision is recorded here, and if built, (1) **Layer 0** — a `Music`-category upload
  like the Nipsey example is matched using its `channel` artist, no dash-parsing involved; (2) Layer 1
  turns a cruft-heavy title into a materially better-ranked list; (3) if Layer 2 ships, a reversed
  title with no usable channel surfaces the correct match. All **verified by driving the real pipeline
  and watching it (`/verify`)**, not by a unit test on the parser. `normalize.py` stays pure, the
  channel signal is a score-arbitrated hint (never an override), and the 0.90 bar is intact — confirmed
  in the diff review.
