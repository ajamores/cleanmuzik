# T-048 — Durable per-track rows for the batch card (landed/gone detail survives a restart)

> **Backlog (untriaged).** Filed 2026-08-19 during the **T-310** build (batch view). Not a bug — a
> deliberate, ADR-sanctioned limitation surfaced while building the card and confirmed in T-310's `/code-review`.
> The card meets its own "Done when" (survives reload + restart); this ticket is the enhancement that would
> make the *per-track row detail* survive too. Related: **T-310** (the card), **T-312** (the durable
> aggregate snapshot), **ADR-027 seam 5** (the decision this ticket would revisit).

- **Status:** todo (backlog — not R2 scope; captured per the scope guard).

## The limitation

T-310's batch card reads two sources in two lanes:

- the **aggregate tally + terminal state** — durable (rebuilt from SQLite via `count_jobs_by_status` →
  `batch_progress_payload`, the T-312 snapshot), so it is correct after a reload **or a backend restart**;
- the **per-track rows** (the Landed / Gone buckets, the live strip) — accumulated **live** off the batch
  SSE stream's stamped `track.*` events (T-305).

Per-track rows are therefore **live-only**. On a true restart the SSE replay buffer is empty, so:

- the tally still shows e.g. "43 landed / 3 gone" (durable), and the card renders whole;
- but the individual landed/gone **rows** are not redrawn — the card shows a durable **count summary**
  ("43 landed and filed in your library") in place of the per-song rows with their album art.

The **"needs you"** bucket is unaffected — parked reviews are durable (T-310 gave the review payload
`playlist_id`+`position`), so they redraw and stay resolvable across a restart.

## Why it's this way (ADR-027 seam 5)

The T-312 reconnect snapshot is **aggregate-only by decision** (a 3-seat design council, 2026-08-18):
seam 5 reserves the *per-track ordered read* for the membership store's backfill path (T-306), not the
reconnect projection. So there is deliberately **no durable per-track read** for the card to rebuild rows
from — only the aggregate counts and the durable reviews. The design gate's screen 05 shows landed rows on
"reopened after walking away," which holds **within a live session** (the stream replays), but not across a
process restart.

## What this ticket would build

A durable per-track read the card can rebuild its buckets from after a restart — e.g. a
`GET /api/playlists/{id}/tracks` ordered projection (position, status, and the display fields the row shows:
title/artist/album/year/genre, `has_art`, landed path). Then the card seeds Landed/Gone rows from it on cold
load, exactly as it seeds the tally from the aggregate snapshot today, and refines live off the stream.

**Decisions this needs (why it's not a trivial add):**

- **Where the display fields live durably.** `track.done`'s tags (title/artist/genre/`has_art`) currently
  ride the SSE event, not a durable column (ADR-015 keeps the landing *receipt* off the reconnect snapshot).
  A durable row read means persisting those fields (a new projection table, or reading them back off the
  landed file's tags / the beets library) — a real design surface, not a column add.
- **Re-paste generations.** The tally already counts only the newest attempt per position (`MAX(rowid)`);
  the per-track read must do the same so a re-pasted list doesn't render two generations of rows.
- **Art.** Landed rows draw a `CoverSwatch` seeded off identity today (real cover bytes are a separate
  deferred follow-up); a durable read should carry enough identity to reproduce the same swatch.

## Why filed, not fixed now

The card's own acceptance (T-310 items 7, 8) is met: it survives reload and restart as **one aggregate
card**, the tally is durable, and every parked track stays visible and resolvable. Redrawing per-track row
*detail* across a restart is an enhancement with its own data-model surface (durable display fields, ADR-015
tension), best taken as its own ticket rather than folded into T-310. No acceptance item requires it.
