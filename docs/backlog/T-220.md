# T-220 — EPIC: Shazam is the tag + art source of record (retire the MusicBrainz/beets tag path)

> **Backlog · EPIC · READY-FOR-BUILD — ADR-033 ratified 2026-08-26.** Filed 2026-08-26 from the
> muziktest head-to-head ([`T-218`](T-218.md)) and the design conversation that followed. Decomposes into
> the wave **T-221 → T-224** (dependency order). The base is set: **ADR-033** (ratified) reverses
> **ADR-005** (beets as tagger) and supersedes the R1.5 "art/lyrics land via beets" rule
> (ADR-024 / spec §3). Build the wave in order; each ticket carries the ADR-030/032 acceptance bar.

## Framing — this is a subtraction, not a port

The important correction, established while writing this spec: **cleanmuzik already identifies with Shazam
and already fetches Shazam's tags and cover on every track.** It is not muziktest's engine we lack —
cleanmuzik's *identification* is richer (three senses + an LLM 2-of-3 vote; muziktest is Shazam-primary +
one witness). What cleanmuzik does is **throw the Shazam tags and cover away** and re-derive everything
through MusicBrainz hydration + Cover Art Archive. This epic removes that detour and uses the data already
in hand. muziktest is a *reference* for the tag-from-Shazam + mutagen-write pattern — not an engine to port.

| | cleanmuzik today | after this epic |
|---|---|---|
| Identify (3 senses + LLM 2-of-3) | built (T-201/202/205/219) | **unchanged** |
| Fetch Shazam tags + `art_url` every track | yes — then discarded (spec §3) | **kept and used** |
| Tag source | MusicBrainz hydration (`_ensure_full_match` → `get_recording`, T-208) — the slow part | Shazam record (already in hand) |
| Art source | Cover Art Archive via `fetchart` (picks a release → wrong-cover class) | Shazam `art_url` (already in hand) |
| Writer | beets | mutagen (ID3/MP3-320) |

## Problem Statement

The acquire pipeline is slow, and its artwork is often wrong — and **neither fault is in identification.**
Both live in tag-and-art *sourcing*: cleanmuzik identifies a track (correctly, via the Shazam + AcoustID +
title senses), then discards Shazam's tags and cover and re-derives them through MusicBrainz. The tag
re-derivation is `_ensure_full_match` → `get_recording` plus a year lookup — serialized calls behind
MusicBrainz's ~1 request/second limit, per track, which stall the whole run whenever MusicBrainz is slow
(the 2026-08-25 head-to-head: **413s** for 16 tracks). The wrong-cover class has the same root: `fetchart`
pulls the image for whichever *release* it picked, so a compilation release yields a compilation cover —
the *Marvin Gaye's Greatest Hits* cover landed on a *Trouble Man* soundtrack track **even though Shazam had
already handed us the correct soundtrack cover URL and we threw it away.**

## Solution

Make the **Shazam record the tag-and-art source of record** for the corroborated majority, retire the
MusicBrainz/beets tag-and-art path, and write with **mutagen**. The three-sense 2-of-3 identification gate
(and the T-219 corroboration fast-path) stays exactly as it is — this epic changes only what happens *after*
an identity is accepted (the `_accept` tail): where the tags and cover come from, and what writes them.

- **Tags from the accepted identity.** When the landed identity is Shazam-corroborated, its artist / title /
  album / year / genre come straight from the Shazam record already fetched this track — no MusicBrainz
  hydration.
- **Art from the accepted identity.** Embed Shazam's `art_url` (already captured, `coverarthq`); fall back
  to the YouTube thumbnail (centre-cropped square) when absent. No `fetchart`, no Cover Art Archive, no
  release selection — which removes the wrong-cover class at the root.
- **AcoustID-only case keeps one thin MusicBrainz call (owner decision, option 1).** When Shazam missed but
  AcoustID + the title still corroborate the identity, there is no Shazam record to tag from, so a single
  `get_recording` by the AcoustID recording MBID supplies its tags + art — **no fan-out, no per-track cost.**
  ~99% of tracks (Shazam hits) never touch MusicBrainz, so its outage no longer stalls acquisition; the
  Shazam-miss minority still tags cleanly and AcoustID's unique coverage (Tower of Power, Ryder × Skepta) is
  preserved. This is muziktest's own answer, and it keeps "MusicBrainz off the critical path" true without
  deleting it.
- **Retire beets.** With tag matching already living in the senses and tag *writing* moved to mutagen,
  beets' reason to exist is gone. Remove it and its `musicbrainz` / `chroma` / `fetchart` / `embedart`
  plugins. AcoustID (the rescue sense) uses the `acoustid` library directly, as muziktest does.
- **Write what Shazam hands us free.** artist / album / title / cover always; year + genre whenever the
  Shazam response carries them (it does — the record just doesn't keep them yet); lyrics best-effort when
  clean. Never a separate slow fetcher for any field. (Genre now comes from Shazam on the auto-path —
  ADR-023's unbuilt LLM-enum genre is re-homed to the polish pass; see Further Notes.)

## The gate, unchanged — this is what already runs

Shazam is one of three senses; auto-land needs 2-of-3 to agree (ADR-021 amendment, T-205). Shazam never
lands alone. This table is the *current* engine; the epic does not touch it — it only changes the tag/art
source in the accepted branches.

| Senses agreeing | LLM? | Outcome | What the epic changes |
|---|---|---|---|
| fp + yt (T-219 fast-path) | **no** | ✅ land | tags/art now from the accepted identity, not MB |
| ≥2 of {yt, fp, shazam} via reconcile | adjudicates | ✅ land | same |
| Shazam among the agreeing senses | — | ✅ land | tags/art from the Shazam record + `art_url` |
| AcoustID-only (Shazam missed) among agreeing | — | ✅ land | tags/art from one thin `get_recording` (option 1) |
| <2 agree / senses conflict | adjudicates → park | → review | review carries YouTube thumbnail + provisional title |

The Frank Ocean / Coldplay cover is safe here as it is today: Shazam says *Coldplay*, the title says *Frank
Ocean* — they disagree, so it never reaches 2-of-3 on a single identity and parks. The corroboration
requirement is what authorises trusting Shazam's tags, exactly as ADR-032 argued for the fingerprint.

## User Stories

1. As the owner, I want a pasted YouTube song to land in Jellyfin in seconds, so that acquiring music is not a wait.
2. As the owner, I want artist/album/title correct, so that the track files itself in the right place.
3. As the owner, I want a decent album cover on every landed track, so that my library grid looks right.
4. As the owner, I want the Shazam cover we already fetch to actually be embedded, so that the wrong-cover class (compilation art on a soundtrack track) disappears.
5. As the owner, I want tags taken from the identity we already accepted, so that we stop paying a MusicBrainz round-trip to re-derive what we already know.
6. As the owner, I want MusicBrainz off the critical path of the common track, so that a MusicBrainz outage no longer stalls my acquisitions.
7. As the owner, I want the existing three-sense identification and its 2-of-3 vote kept intact, so that the reshape does not weaken the accuracy I already have.
8. As the owner, I want a track Shazam misses but AcoustID+title catch to still land with clean tags via a single thin MusicBrainz lookup, so that AcoustID's unique coverage is preserved without reintroducing per-track MusicBrainz cost.
9. As the owner, I want a cover sung over another artist's master (Frank Ocean / Coldplay) to still park, so that the engine never confidently mistags a cover — unchanged from today.
10. As the owner, I want year and genre written whenever Shazam supplies them free, so that I get richer tags at no added cost.
11. As the owner, I want a field Shazam does not supply left blank rather than fetched from a slow service, so that I can fill it deliberately later.
12. As the owner, I want beets removed once tag-writing moves to mutagen, so that the codebase carries no dead heavy dependency.
13. As the owner, I want tags written directly with mutagen (ID3/MP3-320), so that the write step is in-process and fast.
14. As the owner, I want the tool to keep its UI, live progress, review inbox, and Jellyfin landing, so that the reshape changes speed and quality without changing how I use it.
15. As the owner, I want MP3-320 preserved *for this epic*, so that the acceptance compare changes only the tag/art source and not the audio format at once (codec reconsidered separately — T-225).
16. As the owner, I want a review track to still carry the YouTube thumbnail + a best-effort title, so that it is playable and reviewable, never blank — unchanged from today.
17. As the owner, I want the review queue no larger than today's, so that the reshape does not cost me manual clears.
18. As the owner, I want the LLM to stay the occasional adjudicator it already is, so that its cost stays on the conflict branches, not every track.
19. As the owner reviewing later, I want to run an LLM-and-mutagen polish pass over the landed library on my own time, so that subjective/missing tags are added when I choose — this epic leaves that door open, not implement it.
20. As the owner, I want the acceptance bar to be a measured before/after over the real corpus, so that "faster, same-or-better outcomes, better covers" is proven.

## Implementation Decisions

### The wave (dependency order)

- **T-221 — Widen the Shazam record to carry the tag payload.** The record already keeps
  `shazam_artist`/`shazam_title`/`isrc`/`art_url`/`lyrics`; add **album, year, genre** (all present in the
  `track` dict `shazam_runner.py` already fetches — from `sections` metadata and `genres.primary`). Prefer
  what `recognize` returns; call `track_about(track_id)` only to fill a field `recognize` omitted. This is
  the data the tag step consumes.
- **T-222 — Tag + art from the accepted identity in `_accept`.** Replace the `_ensure_full_match`
  (MusicBrainz hydration) tag source in the accepted branches: when the landed identity is Shazam-backed,
  build tags from the widened Shazam record and download+embed `art_url` (→ YouTube thumbnail fallback);
  when it is AcoustID-only, one thin `get_recording` supplies tags + art (option 1). The land decision and
  the senses gate are **not** touched — only the source of the tags/art that get written.
- **T-223 — mutagen ID3 writer + art embed.** A mutagen ID3/MP3-320 tag+art writer (adapts muziktest's MP4
  `Mp4TagWriter` — MP4→ID3 is the real re-implementation) replaces the beets tag-write + `fetchart`/
  `embedart` in the land tail.
- **T-224 — Retire beets + drop the slow fetchers.** Remove beets and the `musicbrainz` / `chroma` /
  `fetchart` / `embedart` plugins once T-221–T-223 carry identity/tag/art. AcoustID (rescue sense) moves to
  the `acoustid` library directly. The single AcoustID-only `get_recording` (T-222) uses `musicbrainzngs`
  directly, not beets — so "retire beets" holds. Year/genre still written from Shazam; no field gets its own
  standalone call.

### Modules — ours, reshaped (not muziktest ported)

- **Kept unchanged:** the whole identification path (`FingerprintTrustSession`, the 2-of-3 reconcile gate,
  the T-219 fast-path, `app/shazam.py` + `shazam_runner.py` + `.venv-shazam`), the downloader + transcode
  front half, the FastAPI job/SSE layer, the review inbox, Jellyfin landing, the `import_song` seam.
- **Changed:** `shazam_runner.py` (widen the record), the `_accept` / `_ensure_full_match` tail in
  `import_seam.py` (tag+art source), `beets_engine.py` (plugin list → removal).
- **New:** a mutagen ID3/MP3-320 tag+art writer.
- **Reference only (not imported):** muziktest's `tagwriter.py` and `authority.canonical_album_for_recording`
  — patterns to mirror, adapted to ID3 and to a direct `musicbrainzngs` call.

### Contracts

- `import_song` keeps its signature and output shape (landed/parked + tags + art-embedded flag), so the
  review inbox, SSE events, and `test_import_seam.py` bind unchanged.
- Corroboration, not raw sense confidence, authorises the tag source: a Shazam record is written as tags
  only when Shazam is among the ≥2 agreeing senses — never off a lone dissenting Shazam vote (ADR-021 Rule:
  Shazam never lands alone; preserved).
- The AcoustID-only tag lookup is exactly one `get_recording`; it must never fan out to per-candidate
  hydration (the T-208 discipline) and must fail-soft to a provisional/review outcome, never block.

### ADR-033 (owner ratifies before build)

A new ADR that: (a) **reverses ADR-005** — beets retired from tag-writing (matching already left it for the
senses; mutagen writes); (b) **supersedes the R1.5 "art/lyrics land via the beets path" rule** (ADR-024
note / spec §3) — Shazam's `art_url` is now the cover source of record, thumbnail the fallback; (c) records
**option 1** — one thin `get_recording` for the AcoustID-only tag source, MusicBrainz retained as a rare
non-fan-out fallback, not a per-track dependency; (d) records the field rule (write what Shazam supplies
free) and its reconciliation with ADR-023's LLM-genre. It does **not** touch the identification gate
(ADR-021/024) or the T-219 fast-path (ADR-032).

## Testing Decisions

- **One seam: `import_song`.** Prior art: `server/tests/test_import_seam.py` (T-219's `test_fast_path_*`).
  New tests assert, at this seam, the **written tags and the art source** per accepted branch — Shazam-backed
  identity → tags/art from the Shazam record; AcoustID-only → tags from the thin lookup; miss → thumbnail +
  provisional. They assert external behaviour (the four+ tag values, which art tier supplied the cover, land
  vs review), never the internal call sequence.
- Fake the network at the sense/lookup boundary (the Shazam record, the single `get_recording`, the art
  fetch), as the existing suite already fakes `shazam_fn` / `dominance_fn` / `reconcile_fn`.
- **Acceptance bar (epic-level, engine-touching → ADR-030/032 bar):** re-run the head-to-head harness
  (`t219_compare.py`, generalised) over the 16-track corpus, before vs after. Prove: materially faster
  (MusicBrainz off the common path), artwork present *and correct* on landed tracks (the Trouble Man cover
  is now the soundtrack, not the compilation), identification outcomes unchanged (same land/park split
  modulo the accepted tag-source change), and the Frank Ocean / Coldplay fixture still parks.

## Out of Scope

- **The identification gate** — the three senses, the 2-of-3 vote, the LLM adjudicator, the T-219 fast-path.
  Untouched. This epic is strictly the tag/art source and the writer.
- **The conversational LLM + mutagen polish pass** (story 19) — owner runs it by hand; R2.5 clean-work.
  This epic leaves the door open (clean authoritative fields, nothing fighting a later edit) but does not
  build it.
- **The download + transcode front half** — unchanged *by this epic*; the codec question is held separate
  (T-225) to keep the acceptance compare single-variable.
- **The migrate/clean release (R2.5)** — the reshaped engine will later sweep the existing library; its own
  release.

## Further Notes

- **Supersedes the framing of [`T-035`](T-035.md)** (Shazam as a *fallback* tier feeding MusicBrainz). That
  ticket predates ADR-024 (Shazam every track) and ADR-021 (senses vote); its evidence — the 4/5 rescue
  table, the Frank Ocean fixture — remains load-bearing and carries into ADR-033.
- **Builds on the engine as it stands:** ADR-021 (LLM adjudicates, senses vote), ADR-024 (Shazam every
  track), ADR-032 / T-219 (corroboration fast-path). This epic sits *downstream* of all of them, in the
  land tail only.
- **Genre authorship — resolved (ADR-033 decision 5).** ADR-023 (LLM genre against a curated enum) was
  ratified 2026-08-09 but **never built**: genre today comes from the `lastgenre`/Last.fm plugin, which this
  epic removes, and the only LLM that runs (the ADR-021 reconciler) fires on conflict tracks only and
  authors identity, not genre. So genre auto-writes from **Shazam** (free, every Shazam hit, happy path
  included); ADR-023's LLM curated-enum genre is re-homed to the deferred polish pass, not repealed. This is
  a strict simplification of the auto-path, not a new constraint.
- **Codec reconsideration — sibling ticket T-225 (not this epic).** A YouTube rip is already lossy
  (~128–160 kbps), so transcoding it *up* to MP3-320 adds no quality — it pays a second lossy encode + CPU +
  larger files. The cheapest-and-highest-quality path is to not re-encode at all: keep the best source
  stream and remux into a taggable container. Reverses the MP3-320 ADR and mixes library formats, so it is a
  separate owner decision, deliberately kept out of the engine reshape.
- MP3-320 means the writer is mutagen's ID3 path, not muziktest's MP4 — the one genuine re-implementation.
