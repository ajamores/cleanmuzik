# T-216 — Bound the Cover Art Archive fetch (the biggest per-track latency lever)

**Status:** untriaged, **buildable anytime** — safe, non-engine, best-effort art. New finding from the
2026-08-19 live-batch profile (agent pipeline profile against a real 29-track run); **not** part of the
T-208/214/215 speed family, and **not** the R2.5-deferred engine change (it never touches beets or identity).

## Problem
On a live batch the cover-art stage was the single biggest *variable* cost — **~36s on one track**, and it
explained the "art-bearing tracks slow, `no cover art found` tracks fast" pattern. The cost is structural, in
`app/artwork.py :: fetch_cover_art`:
- `_MAX_CAA_RELEASES = 3` (`artwork.py:45`) — a recording is tried against up to 3 release MBIDs, **each a
  blocking GET** on the synchronous (ADR-001) import thread.
- `timeout: int = 10` (`artwork.py:82`) — 10s per attempt, and CAA's `/front` **307-redirects to
  archive.org backends** (`allow_redirects=True`, `artwork.py:104`) that are frequently slow, so a stall
  waits the full budget per hop.
- Worst case ≈ 3×10s (CAA) + iTunes fallback ≈ **~40–50s** for one track's art.

The front cover is near-identical across a recording's releases (the code's own note, `artwork.py:42–44`), so
trying three buys almost no quality and risks stalling the whole pipeline.

## Approach (1 constant, no logic change) — revised after code review
**The timeout is the tail-bound; the release cap preserves recall.** The first draft also dropped
`_MAX_CAA_RELEASES 3 → 1`, but code review (2026-08-19) caught that this conflates cover *quality* with cover
*availability*: the top release MBID may carry no front cover where a later one does, so cap=1 is a real
art-**recall** regression, and it promotes the iTunes fallback to primary while a tighter timeout starves it.
Since a coverless release **404s fast**, the extra releases cost ~nothing on the common path — only the *slow*
release costs time, and that is what the timeout bounds. So:
- **Keep `_MAX_CAA_RELEASES = 3`** — recall unchanged.
- Default `timeout: int = 10 → 5` in `fetch_cover_art` — the actual lever. `requests` applies it to connect
  **and** each read, and with `allow_redirects` a CAA→archive.org hang pays it per hop, so 5s caps the stall
  well under 10s while leaving the iTunes fallback (search + a 1200×1200 image GET) real headroom. Caller
  (`import_seam.py:480`) passes no timeout, so the default applies. Worst case per release 30s → 15s; the
  common fast-404/200 path is unchanged.

## Done when
A slow CAA release can no longer stall the import thread for 10s/hop (bounded to 5s); art **recall** is
unchanged (all releases still tried, iTunes fallback intact); a missing cover still degrades to `None` and
never blocks or fails a landing. Cap test asserts the constant (`tests/test_artwork.py`), plus a guard that
the default timeout is the bounded value. All existing land/park outcomes unchanged (art is Door B, decorative).

## Why it's safe
Art is best-effort — worst case is a missed cover, never an un-land or a mistag. No ADR governs the release
cap or the timeout. Non-engine, so the T-208 R2.5 deferral doesn't apply. Batch-amplified: bounding the tail
lifted a live run's per-track wall-clock from ~39s to ~26s (art landing in ~5s where a slow release had
stalled it). Recall preserved.
