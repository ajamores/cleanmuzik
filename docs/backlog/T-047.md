# T-047 — Harden the T-304 pending-append reconcile (give-up budget, exactly-once, failure vs. miss)

> **Backlog (untriaged).** Filed 2026-08-17 from a `/code-review high` pass during the T-303 build. Three
> latent defects in the **already-shipped T-304** reconcile machinery (`reconcile_pending_appends`,
> `resolve_item_id`, `MAX_APPEND_ATTEMPTS`). Not introduced by T-303 — T-303 only *reuses* the seam — so
> they were filed rather than folded into that ticket's scope. Related to **T-312**, which already owns
> surfacing the give-up state to the batch card.

- **Status:** todo — untriaged. Owner to decide priority (candidate: fold into T-312).

## The three findings

1. **The give-up budget (`MAX_APPEND_ATTEMPTS`, cap 20) is spent by the fast on-land drain, not paced by
   the ~25s tick its comment assumes.** `_drain_after_land` (limit 5, oldest-first) re-resolves the oldest
   pending member on nearly every land. A fast batch of short/cached videos can burn all 20 attempts on the
   earliest member within ~20 rapid lands — well before Jellyfin finishes indexing it — and drop it from
   `list_pending_appends` **permanently**. `append_attempts` is used as a proxy for wall-clock time, but the
   two drain paths run at wildly different cadences. *Candidate fix:* key ret/give-up on **elapsed time
   since land**, not raw attempt count; and/or make the counter resettable.

2. **Exactly-once is not guaranteed: the Jellyfin append happens *before* `mark_member_appended`.** If the
   stamp raises (row deleted concurrently) or the process crashes between the two, `jellyfin_item_id` stays
   NULL and the next pass **re-appends the same item** — a duplicate playlist entry (the Jellyfin endpoint
   "happily double-adds," per the seam's own docstring). The append→stamp pair is not atomic. *Candidate
   fix:* stamp-then-append with a compensating check, or make the append idempotent by pre-checking
   membership in the Jellyfin playlist.

3. **`resolve_item_id` collapses a genuine Jellyfin failure (5xx / timeout / 401) into the same `None` as a
   legitimate "not indexed yet" miss.** So a transient outage or a rotated API key **burns give-up attempts**
   on perfectly-indexable files; a key fixed an hour later leaves every append from that window permanently
   stranded. *Candidate fix:* distinguish "confirmed absent" from "call failed" and only count give-up
   attempts for the former.

## Why filed, not fixed now

All three predate T-303 and live in T-304's shipped seam. Fixing them means changing the give-up/retry
contract and the resolve failure-mode — a design decision with its own acceptance surface, best taken with
T-312 (durable batch state + reconnect), which already surfaces the give-up warning to the card. T-303's
skip path adds members whose files are **long-since indexed**, so they resolve on the first drain and do not
themselves exercise the give-up ceiling — the review confirmed T-303 does not worsen these.
