# T-045 — Theme switcher + colorway registry (pick Dark / Light / System, persisted)

> **Backlog (untriaged).** Filed 2026-08-16. Owner endorsed the shipped **ADR-018 dark console skin**
> (near-black ground + cyan accent) as the wanted dark mode while reviewing the T-310 batch-view
> design-gate screens, and asked for a **manual theme switch** plus **more colorways eventually**.
> Independent of R2 (Playlists) — **build after R2 ships**, not part of T-310.

- **Status:** todo — untriaged. **Timing decided:** after R2.
- **The gap.** The app themes by stamping `data-theme` on the root — `[data-theme='light']` and
  `[data-theme='dark']` token blocks already exist in `client/src/index.css` — but there is **no UI
  control to set it, no persistence, and only two hard-wired themes**. Today the theme is derived from
  the OS (`@media prefers-color-scheme`), so a light-OS machine never sees the dark console colorway the
  owner wants. Verify the current token structure against `index.css` before building — it may have
  drifted.
- **Decided behaviour (owner, 2026-08-16):** the switcher offers **Dark / Light / System**, and the app
  **defaults to Dark** (this console colorway) for everyone, not to the OS preference. "System" remains
  available as an explicit choice (follow `prefers-color-scheme`). The choice **persists** (localStorage)
  and applies **before first paint** (no flash of the wrong theme on load).
- **The shape of a fix (undecided in detail).**
  - **A colorway registry**, not hard-wired themes: each theme is one named token block; the switcher
    lists them. Adding an "eventually" colorway becomes a one-block-plus-one-entry change, not a rewrite.
    Dark and Light are the first two entries; the near-black+cyan dark is the default and the reference.
  - **A picker control** in the console rail (its foot, by the pipeline legend, is the natural home) —
    scoped at the design gate (ADR-016) since it changes a visible flow/state.
  - **Persistence + pre-paint apply** (an inline head script or equivalent) so the stored choice wins
    over the OS default with no flash.
  - Almost certainly an **ADR-018 amendment** (it owns the console skin / theming), recording: Dark as
    the default (a reversal of today's OS-derived default), the registry pattern, and how "System" fits.
  - Open questions: the exact control affordance (toggle vs. menu — a menu scales to N colorways better
    than a toggle); whether "System" is a first-class registry entry or a meta-mode above the registry;
    keeping every future colorway legible (contrast + working accent on its own ground, per the tokens'
    existing discipline).
- **Related:** builds on **ADR-018** (console skin / the dark tokens). Owner taste is recorded in the
  `dark-console-colorway` memory. Not to be conflated with the R2 UI (T-310).
- **Done when:** the owner can switch **Dark / Light / System** from a control in the app; the app opens
  in the dark console colorway by default regardless of OS; the choice survives a reload with no wrong-
  theme flash; and adding a third colorway is a single named token block plus one switcher entry.
