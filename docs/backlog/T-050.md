# T-050 — Harden `has_lyrics` against the same in-memory-lag as the genre report

> **Backlog (untriaged).** Filed 2026-08-20 during the **T-309** build (genre-report read-off-disk),
> surfaced by T-309's `/code-review` (finding 1). Not a bug in the shipped fix — a **same-class
> follow-on** for a field T-309's Done-when did not cover. Related: **T-309** (the genre fix it
> parallels), **T-037** (the origin defect cluster), **T-103** (the verify that diagnosed the lag).

- **Status:** todo (backlog — not R2 scope; captured per the scope guard).

## The gap

T-309 hardened one field of the `track.done` receipt against a proven defect: a plugin writes a tag
to the landed file, but the in-memory `item` the seam snapshots (`_landed_tags`,
`import_seam.py:~1338`) still reads the pre-write value, so the payload under-reports. T-309 fixes
`genre` by reading it back off disk (`_genre_on_disk`).

`has_lyrics` is derived from the **same in-memory item** (`bool(getattr(item, "lyrics", None))`). The
`lyrics` plugin also writes to the file, so if `item.lyrics` lags its disk write the way `item.genre`
did (T-103), `track.done` would report `has_lyrics: false` on a track whose landed file carries
synced lyrics.

## Why it's not a proven bug today (why T-309 is complete without it)

- The lyrics lag is **unobserved** — T-103 diagnosed the discrepancy for `genre` only. Whether the
  `lyrics` plugin's write races the snapshot the same way is a hypothesis, not a measured defect.
- T-309's Done-when is scoped to the genre field (acceptance item 10). Widening it to lyrics without a
  reproduced discrepancy would be building the nearest thing, not the asked thing.

## What this ticket would build

- Reproduce (or refute) the lyrics lag with a T-103-style verify: land a track with known synced
  lyrics, assert the `track.done` `has_lyrics` against the tag actually on disk.
- If it reproduces, add a guarded read-off-disk for lyrics presence, mirroring `_genre_on_disk` (same
  best-effort `MediaFile` open, degrade to the in-memory field on error).

## A note on the broader shape (review finding 2, declined for T-309)

The review also floated refreshing the whole item from disk once (`Item.read()`) instead of a
per-field helper. Declined for T-309: a blanket re-read would clobber in-memory fields the seam sets
intentionally, and the per-field guarded helper matches the existing read-off-disk idiom. If a
*third* field ever needs the same treatment, revisit whether a scoped multi-field disk parse earns
its blast radius — but not before.
