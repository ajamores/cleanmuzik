# T-043 — `scrub` plugin: strip surviving junk ID3 frames on write

> **Backlog (post-R1) · untriaged.** Tag-quality, not R1.5 spine (R1.5 is the identity engine).
> Surfaced by the 2026-08-10 beets capability audit. Triage into a release when tag-quality or
> **R2.5 migrate/clean** is scoped. See `README.md` for how this directory works.

- **Status:** untriaged (captured, not committed to a release).

- **The gap.** We set `from_scratch: True` (ADR-013) believing it gives a clean write — but
  `from_scratch` clears the **beets Item model**, not arbitrary ID3 frames already on the file. yt-dlp's
  `FFmpegMetadata` writes the YouTube description / `purl` / comment text (`app/download.py:~289`), and
  `-map_metadata 0` carries them through transcode (`app/transcode.py:~12`). MediaFile's write only
  manages known fields, so those unmanaged frames **survive** onto the landed MP3 — invisible junk
  (YouTube URLs, descriptions) riding along in the tags.

- **The fix.** Enable beets' **`scrub`** plugin with `auto: yes` — it strips *all* tags then rewrites only
  the DB-tracked ones, a genuinely clean write. `beets.readthedocs.io/en/stable/plugins/scrub.html`

- **Why it's safe for our architecture specifically.** `scrub` runs in the import stage, but we embed
  cover art in a **post-run** step (`finalize_outcomes` → `artwork.py`), so scrub cannot wipe our
  embedded art (it has already run before the art is written). Confirm this ordering in the build.

- **Verify.** Land a YouTube rip, then inspect the MP3's frames (e.g. `ffprobe`/`mid3v2 -l`) — assert no
  `purl`/description/comment frame remains, and that art + synced lyrics + standard tags are intact.

- **Cross-ref.** Sibling audit findings: T-042 (`replaygain` loudness). Migrate-job plugins (`mbsync`,
  `duplicates`, `fromfilename`) are folded into the "Migrate + clean" idea in `README.md`.
