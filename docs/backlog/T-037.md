- **Status:** todo — **filed unreviewed 2026-07-28, owner has not triaged.** Two independent defects on

- **The subject.** Jay-Z — *Wishing on a Star (feat. Gwen Dickey)*
  (`https://youtu.be/ZyDslhDin4s`) auto-tagged and landed at
  `/mnt/c/Users/aj_am/Music/CleanMuzik/Jay-Z/Wishing on a Star (feat. Gwen Dickey).mp3` — 323 kbps,

## Defect 1 — the same artist lands under two different folders

The library now holds **both** `JAŸ‐Z/` (from *Coming of Age*, landed 2026-07-19) and `Jay-Z/` (this
track). Same human, two directories, so **Jellyfin will list two artists** and neither page shows the
full discography.

- **Cause (probable, not verified).** beets derives the path from the MusicBrainz *artist credit* on the
  matched release, and MB genuinely records this artist's credit differently per release — the stylised
  `JAŸ-Z` on some, plain `Jay-Z` on others. So both are "correct" per the match; the split is a
  consequence of trusting per-release credit for the *directory* name.
- **Why it matters more than it looks.** It is invisible on the first track by an artist and appears on
  the second — so it will keep accruing quietly as the library grows, and every occurrence is a manual
  merge later. The owner's library is the point of the product.
- **The shape of a fix (undecided).** beets' `%aunique`/path-format options and the `albumartist` vs
  `artist` distinction are the obvious levers; an artist-credit → canonical-name normalisation
  (ASCII-folding stylised glyphs, per ADR-019's note that folding affects ranking not identity) is the
  other. **Do not** pick one here — this needs a decision recorded as an ADR, because it binds every
  future path the app writes.

## Defect 2 — no genre tag was written

`genre` is absent on the landed file. `album` is absent too. The `lastgenre` plugin is loaded (the boot
smoke check confirms all six plugins), and **T-106's own July artifact recorded `genre Hip Hop`** on the
Nines track — so this is a change in behaviour, not a feature that never worked.

- **Candidate causes, none verified.** Last.fm has no tags for this recording; the owner's
  `LASTFM_APIKEY` is being rejected (it is present in `.env`); `lastgenre`'s source/fallback settings
  don't cover a singleton import; or the absent `album` and absent `genre` share a cause upstream in
  what the match returned.
- **Cheap first probe.** Re-run a track that previously *did* get a genre and compare — if it also comes
  back bare, the plugin or the key regressed; if it doesn't, this is per-recording Last.fm coverage and
  arguably not a defect at all.

## Also observed on the same file, deliberately NOT filed as a defect

The landed MP3 carries the full YouTube `SYNOPSIS`/`DESCRIPTION` (label marketing copy and social
links), a `lyrics-XXX` block, and the raw `Acoustid Fingerprint`. This is `FFmpegMetadata`
(`download.py:289`) doing what it was asked — the embed is **load-bearing** per `learnings.md`, so a
weak/absent match still leaves usable tags. Stripping the description fields is a taste call, not a bug.
Raise it separately if the owner wants the library tidier.
