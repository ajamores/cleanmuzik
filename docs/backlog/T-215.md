# T-215 — Hoist Shazam to run during the beets candidate lookup (safe actual-speed)

**Status:** untriaged, **buildable anytime** — safe, non-engine, independent of any release. From the
T-209 speed finding + the 2026-08-13 design council (the low-risk half of the old T-208).

## Problem
Shazam runs *inside* `choose_item`, i.e. strictly **after** the ~8–9s beets candidate lookup finishes,
adding its ~1.4s (and an up-to-8s hang tail) on the critical path. But `shazam_sense.recognize` needs only
the staged MP3, which exists before `session.run()` — so it can run *concurrently* with the beets lookup
that's already happening.

## Approach (~15 lines, rides the existing `shazam_fn` seam → record byte-identical)
- In `run_pipeline` (`jobs.py`), right after `transcode_fn` returns the MP3 and before `import_fn`, submit
  `shazam_sense.recognize(mp3)` to a single-thread executor / `threading.Thread`.
- Pass `shazam_fn=lambda _p: future.result(timeout=...)` into `import_fn`; `_reconcile` already calls
  `self.shazam_fn(...)` once per track — it becomes a cache-read of the already-running (or finished) future.
- Zero change to the reconcile logic, the 2-of-3 gate, or `_agreeing_senses` — the record is only *computed
  earlier*. **Reap/kill the future on every exit path (park / error / scan-fail) in a `finally`.**

## Done when
Shazam runs under the candidate-lookup window (~1.4–2s off the gate) **and** a Shazam hang no longer sits on
the critical path (it expires under the MB wait); all T-209 land/park outcomes byte-identical.

## Why it's the safe one
It never touches beets or the tagging engine (that's [`T-208`](T-208.md)); correctness is unchanged by
construction. Value is modest seconds plus real worst-case-tail protection.
