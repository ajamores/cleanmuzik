# T-208 — Collapse the MusicBrainz candidate fan-out (the engine-change speed lever)

**Status:** **the primary speed lever (owner-chosen 2026-08-23)** — T-218 measured it as 80–90% of the
gate and [`T-215`](T-215.md) (Shazam hoist) is refuted, so the old "build only after the safe items ship"
gate is gone. Owner opted for **this within-beets fix** over the bigger muziktest model (T-218 Lever B).
Still the **only** speed piece that changes the tagging engine → real correctness risk, clears its own
gate alone, does **not** ride R2's scope; engine-touching → **R2.5-gated**. Opened by T-209 (2026-08-12),
scoped by a design council (2026-08-13); [`T-214`](T-214.md) (narration) is an independent perceived-speed
item, not a prerequisite.

> **T-218 named this the target (2026-08-23).** Measured: the MB fan-out is **80–90% of the gate** in
> every run and its **entire variance** — the other senses are a stable ~6–8s floor; MB swings 6s→80s
> with a per-call tail to 34s. The clincher: a *dominant-fingerprint auto-land* still made **11**
> serialized MB round-trips hydrating candidates it discarded. The estimate below (~8–9s) was optimistic;
> the real fan-out cost is larger and tail-heavy. Endpoint-classified: **all calls are `recording/<id>`
> identity hydration** (zero `release/`), and beets **re-hydrates the same MBID 2×** with no session cache
> — so the scope is (1) hydrate only the dominant/chosen recording, (2) de-dupe within the session. See
> [`T-218`](T-218.md) for the breakdown; a per-call MB **timeout** (→ [`T-210`](T-210.md)) is a cheap
> orthogonal lever if this slips. **Bigger alternative — the muziktest model (MB out of identity, album-
> only) — needs an ADR against ADR-005, tracked in T-218's verdict, not here.**

## Problem
The R1.5 identity gate is ~16–20s; the reconcile *senses* are cheap (dominance 0.6s · Shazam 1.4s · ISRC→MB
0.4–3.4s · Haiku 2–4s). The fat is the **~8–9s beets candidate lookup**, and it is **not** a dependency
chain — it is **fan-out**: up to 5 *independent* MusicBrainz `track_for_id` hydrations, one per fingerprint
candidate, serialized only by MB's global **1/sec** limit. Cutting the *call count* is the lever (threads
can't beat an external rate limit). **The repo already fixed the identical waste on the re-search route** —
`mb_search.py` finding #4: 27s → ~1s by building `TrackInfo` from the search response instead of hydrating
each id. The **acquire path never got it**.

## Approach (~4–5s; gated on the §7 acceptance corpus proving byte-identical auto-land outcomes)

**Owner design decision (2026-08-23), plain-language:** the audio fingerprint already hands back the
winning recording id plus runner-up guesses. Stop paying MusicBrainz for full details on all of them.

- **Confident match (auto-land) → hydrate the winner only.** Fetch full tags for the one recording the
  fingerprint picked; skip the other ~9 lookups entirely. This is the bulk of the speed win.
- **Weak match (park) → hydrate the top 3 candidates, then park to review.** Not the full ~10, not zero.
  Rationale: the T-218 Franklin fixture proved weak-match guesses are often wrong (the real answer was
  *off* the candidate list — owner re-searched), so a full fan-out is waste; but a cap of 3 keeps the
  one-click pick for the close-but-just-under-threshold cases. **Re-search stays the fallback** when the
  3 are wrong (the `POST /api/reviews/{id}/search` route already exists).
- **De-dupe within a session.** T-218 caught the same MBID hydrated 2× in one track (no cache) — collapse
  repeats before hitting MB.
- **Mechanics (unchanged from the original scoping):** give the `musicbrainz` plugin a thin
  `item_candidates` that reads `track_id/title/artist/length` off the search response (the `mb_search.py`
  technique), and **defer the one full `get_recording` to the recording that actually lands** — extend
  `match_for_recording` (`import_seam.py:1162`) to hydrate the accepted candidate for full tags
  (load-bearing: a thin winner must be re-hydrated or tags go missing).
- Fold-ins: fpcalc dedup vs chroma's cached fingerprint (`import_seam.py:26–30`); `cache_control` on the
  reconcile system prompt (`reconcile.py:60`).

## Done when
Candidate stage collapses (auto-land: ~10 MB calls → 1; park: → ≤3) **with zero change** to the §7
land/park *decisions* (re-run the T-209 corpus, prove byte-identical auto-land outcomes), and the review
card still shows candidates to pick from on the park path (now the top 3, with re-search as the fallback).

## Not
Cross-track concurrency (ADR-001). Dropping the `fp` sense or the fingerprint MBID. The "skip Shazam/Haiku
when fp is dominant" shortcut — fp is dominant on the *wrong* recording in the Pa Salieu case, so it
detonates the marquee override. Local MB mirror = **R3** only (removes the limit entirely; a few-hundred-GB
Postgres, absurd on the Phase-0 laptop). Relatedly: [`T-210`](T-210.md) (shared MB limiter) is a prerequisite
if ISRC→MB is ever folded into the candidate-lookup window.
