## Two corrections this ticket produced

Both were found by the *act of citing a line number*, not by any review, and both are logged in
`docs/learnings.md` 2026-07-30:

1. **`.env.example` claimed `ACOUSTID_APIKEY` buys "higher rate limits". It buys nothing** — chroma
   passes its own hardcoded key into every lookup; the config key is the *user* key for submission,

   disagreed in the repo for weeks. **Fixed in `.env.example`.**
2. **This ticket's own filing carried a claim the source refutes** — that `tag_item` "internally
   calls `item_candidates`". True only *without* `search_ids`. Corrected in `docs/engines/beets.md`
   §1, and the ticket text below is left as filed so the correction has something to point at.

## What this ticket exists to prevent

T-103 slice A cost roughly a session's worth of rework, split across three causes. Only one was
genuine new ground; the other two were **documentable and were not documented**:

1. **A project rule stated absolutely, without its scope.** `architecture.md:35`, `spec.md:29` and
   `r1/tickets.md:132` all say *"never call `autotag.tag_item` directly"*. The reason is real and
   import-specific — you lose the plugin stages, so no cover art and no genre. But stated as a flat
   "never", it also steers away from cases it was never about (a *search* lands nothing and runs no
   stages). **Fix: give the rule a scope line, not a softer verb.**
   *Nuance worth preserving:* the rule's conclusion was right here anyway, for an unrelated reason —
   `tag_item` internally calls `item_candidates`, which is the 27-second path. Using it would have
   been slower, not cleaner. The rule misfired on its reasoning while landing on the right answer,
   which is exactly the kind of thing that is invisible until it is written down.
2. **beets' request behaviour, nowhere in the repo.** The 1.0 req/s MusicBrainz limiter, that
   `tracks_for_ids` is *not* batched (one HTTP call per id), and that the limiter is a **shared token
   bucket** — so a search on the web thread starves the acquire pipeline. Discoverable only by reading
   beets' source or timing the running app. See `docs/learnings.md` 2026-07-30.
3. **Which beets config is global vs per-plugin.** `musicbrainz.search_limit` is a *per-plugin* node.
   The wrong assumption ("it's global, so I mustn't touch it") is what motivated a fork.

## What to write

One page per engine under `docs/engines/`, each answering the same four questions — **capabilities, hard
limits, cost model (what one call actually costs in requests/time), and the gotchas already paid for**:

- **beets** — the import seam vs the read/search API; which calls fan out into N requests; rate
  limiting; global vs per-plugin config; the `tag_item` scope note; what the plugin stages provide
  (`chroma`, `lastgenre`, `fetchart`, `embedart`, `lyrics`) and what is lost by bypassing them.
- **MusicBrainz** — the search API's real behaviour (it almost never returns zero results; it matches
  loose tokens — see the ADR-020 amendment), the recording-vs-release distinction that ADR-010 turns
  on, `artist_credit` being underscored by beets' client, rate limits, and what a search response
  carries versus what a per-id lookup adds.
- **ShazamIO** — capabilities and limits, ahead of the ADR-019 Shazam tier. **Note this one is
  currently un-evidenced in the repo**: unlike the other two there is no spike behind it, so this page
  starts as "what we need to find out", not "what we know". Do not write confident claims into it.

**Sourcing rule, and it is the point of the ticket:** every non-obvious claim carries how it was
established — measured, read from the library's source (with a file path), or assumed-and-unverified,
labelled as such. A confident rationale is precisely what stops the next reader re-checking it; that
failure mode is already on record twice (ADR-010's cover art, and this session's fork justification).

## Also raised, un-triaged

The owner asked whether **graphify** (`https://github.com/Graphify-Labs/graphify`, already installed
as a skill) would help here. Assess in this ticket rather than guessing: it builds a queryable graph
over a codebase, so the honest question is whether pointing it at **beets' own installed source** —
not this repo — would have surfaced the `tracks_for_ids` fan-out. This repo's own docs were not where
the missing knowledge lived, so indexing *this* repo would not have prevented today's rework.

### Assessment (2026-07-30): **no — not for this.** Reconsider only on a recurring trigger.

**How the fan-out was actually found while writing `docs/engines/beets.md`** — three steps, plain
`grep` and `Read`, a couple of minutes:

1. `grep -n "def tracks_for_ids" beets/metadata_plugins.py` → the base implementation at `:261-270`.
2. Read ten lines: `return (self.track_for_id(id_) for id_ in ids)` — a docstring that says *"Batch
   lookup"* over a generator that is not batched.
3. `grep tracks_for_ids beetsplug/musicbrainz.py` → **absent**, so the base implementation stands.

**So the knowledge was never hidden — it was ten greppable lines.** What was missing was not a map
of beets; it was **the question "how many HTTP requests does this method make?"** Nobody asked it
until a 27-second latency asked it for them.

That is the whole assessment. graphify would have made step 1–3 marginally cheaper — it maps call
relationships, so `item_candidates → tracks_for_ids → track_for_id` would have been one query
instead of three greps. It would **not** have volunteered "and that costs N requests", because a
call graph shows *what calls what*, not *what that costs*. **The bottleneck was the question, and a
graph does not supply questions.**

Against that marginal gain: indexing a dependency the size of beets is a real cost, the index goes
stale on every version bump (and the pin is deliberate — `beets.md` §6 lists what to re-verify), and
it would sit in the repo as a second, unversioned source of truth about a library we don't own.

**The durable fix is the one this ticket already delivers:** `docs/engines/beets.md` §2 records the
answer with `file:line` provenance, so the next reader doesn't trace anything — they read it. A
graph would have to be re-queried by someone who already suspected the problem.

**Reconsider if** beets-source spelunking becomes *recurring* rather than twice-in-a-project — R2's
migrate + dedup sweep is the plausible trigger, since it drives beets much harder than acquire does.
At that point the question changes from "would this have caught one bug" to "is there a standing
need to navigate this dependency", which is the question graphify actually answers well.
