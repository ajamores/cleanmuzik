# T-217 — Debounce the Jellyfin library scan to once per batch

**Status:** untriaged, **buildable anytime** — safe, non-engine. New finding from the 2026-08-19 live-batch
profile. Independent of the T-208/214/215 speed family and the R2.5 engine deferral.

## Problem
Every landed track fires a **full** `POST /Library/Refresh` (`jobs.py:895` → `jellyfin.py:173`). On a 29-track
batch that is 29 overlapping full-library scans. The POST itself is cheap (204, the scan runs async
server-side), so this is **not** a large pipeline wall-clock cost — but it thrashes the Jellyfin indexer and
slows the concurrent playlist-drain `/Items` listings.

## Approach
- Gate the per-track `scan_fn` on `playlist_id IS NULL` — keep the immediate scan for **single-song R1 jobs**
  (preserves the spec §5/§6 T-010 "appears in seconds" contract).
- For batch members, fire **one** `/Library/Refresh` at batch settle — a new trigger in
  `_settle_batch_after_member` when the derived state is `done` (`jobs.py:535`). There is currently no
  batch-end scan hook; this adds the single trigger.

## Safe because the append seam does NOT depend on the per-track scan
`reconcile_pending_appends` (`jobs.py:288–455`) resolves Jellyfin item ids by **retry**, decoupled from the
scan: `resolve_item_id` is a single non-blocking attempt (`jellyfin.py:344–419`), retried on later worker
ticks (the on-land drain `jobs.py:916`, the background tick, the boot sweep). It needs only that Jellyfin has
*eventually* indexed the file — one scan at batch end delivers that for the whole tail. (Agent-verified,
2026-08-19 profile.)

## Done when
A batch fires exactly one `/Library/Refresh` (at settle), single-song R1 jobs still scan per-land, and a
parked-then-resolved track still backfills into its playlist. Direct pipeline saving is small; the real win is
removing 29-scan indexer thrash.
